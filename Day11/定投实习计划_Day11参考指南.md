## 一、1 万元资金够不够

### 1.1 新建分析工具：smile_curve_analyzer.py

在 `tools/` 下新建 `smile_curve_analyzer.py`。

> 💡 动手前先想清楚两件事：
> 1. **别重复造轮子**：`tools/analyzer.py` 里已经有 `backtest_dca()`（历史回测）。新工具要的是"微笑曲线覆盖度"分析，能复用 `analyzer.py` 的回测就复用，不要复制一份同样的回测逻辑。
> 2. **10,000 元是硬上限**：这是出资人实出资，任务书定为 `500×20`、以 `config.py` 为准。所以下面"方案 B 追加金额"等于要出资人再追加资金——除非出资人明确同意，否则不可行，分析时把它当"假设情景"而非默认选项。

这个工具至少接收两个核心参数（其余用默认值即可）：

- `etf_code`（如 中证五百 ETF `510580`）
- `total_amount`（如 `10000`）

输出：

- 历史最大跌幅 + 发生时间
- 完整微笑曲线需要多久、总投入多少
- 两个建议方案：
  - **方案 A**：降低每期金额，延长周期覆盖微笑曲线
  - **方案 B**：保持每期金额，追加总投资

**工具设计要求**：

```python
def analyze_investment_plan(etf_code, total_amount, interval_days=14, per_amount=500):
    """
    分析给定总投资金额能否覆盖一条完整微笑曲线。

    返回：
    - 最大跌幅（%）
    - 完整微笑曲线所需月数
    - 完整微笑曲线所需总投入
    - 方案A：降低每期金额后的月数 + 每期金额
    - 方案B：追加金额后需追加多少

```

**分析逻辑**：

1. akshare 拉取 ETF 过去 5 年历史数据
2. 找到跌幅最深的一段（最大回撤）
3. 模拟定投：每 14 天投 ¥500，算出覆盖这段微笑曲线需要多少期、共投入多少
4. 用总金额和所需投入对比，判断够不够
5. 如果不够，给出方案 A（减金额延周期）和方案 B（追加金额）

## 二、PE < 30% 时，止盈资金怎么分批加回

> **先对齐任务书（重要）**：任务书 §十二「止盈后资金管理」第 3 条已经定了大方向——*"等 PE 近 5 年分位回落至 30% 以下，再分批把止盈资金加回"*。也就是说：**"要不要加回"任务书已经拍板了（要加回）**，Day11 不重新决策是否加回，只决定"分批加回"的**两种执行方式**选哪一种。

### 2.1 先看现状：pe_low 提示词已经在代码里

> ⚠️ 别去翻 Day6 报告的"页码"——那些是 Markdown，没有页码。当前真实的 pe_low 提示词就写在代码里。

打开 `tools/inspector.py`，找到 `inspect_once()` 里这一行（约第 124 行）：

```python
elif pe_pct < 30:
    result["pe_alert"] = f"pe_low: 低估区间({pe_pct:.1f}%)，可分批加回"
```

这就是现状：已经会提醒"可分批加回"，但**没有定义"加多少、什么时候加、上限多少"**。Day11 要补的正是这部分参数。再对照 Day 9 报告 §A.3，确认 PE 阈值逻辑（>70% 推 `pe_high`、<30% 推 `pe_low`、区间不提醒、PE 不触发任何卖出）目前是对的，**不要动它**。

### 2.2 两种执行方式，选一条

PE < 30% 时，货基里的止盈资金按"分批加回"执行，但**怎么加**有两种做法，核心差异是"什么时候加、加多少"：

---

**方案 A：等深坑——PE 极度低估时加仓**

| 规则 | 内容 |
|------|------|
| 触发条件 | PE 分位 < 20%（不是 < 30%，门槛更高） |
| 加仓上限 | 货基余额的 50%，单次最多 ¥500 |
| 停止条件 | PE 回到 30% 以上，或货基清零 |
| 性质 | 只在极端低位出手，次数少、单次可能大 |
| inspector pe_low 提示词 | "市场极度低估（PE分位 < 20%）。你有 ¥__ 在货基里，可考虑额外加仓 ¥__（不超过 ¥500，且不超过货基的 50%）。是否加仓、由你判断。" |

---

**方案 B：分批入场——PE < 30% 开始，每期加一点**

| 规则 | 内容 |
|------|------|
| 触发条件 | PE 分位 < 30%（先到先加） |
| 加仓上限 | 每期不超过 ¥300，也不超过货基余额的 30% |
| 停止条件 | PE 回到 30% 以上，或货基清零 |
| 性质 | 门槛低、每次少，在低估区间内分散进入 |
| inspector pe_low 提示词 | "市场处于低估区间（PE分位 < 30%）。你有 ¥__ 在货基里，可在本期定投之外额外加仓 ¥__（不超过 ¥300，且不超过货基的 30%）。是否加仓、由你判断。" |

---

**对比**

| | 方案 A 等深坑 | 方案 B 分批入场 |
|--|-----------|-------------|
| 触发门槛 | PE < 20%（更保守） | PE < 30%（更积极） |
| 单次上限 | ¥500 | ¥300 |
| 次数 | 少 | 多 |
| 均价风险 | 可能买在半山腰 | 分批平滑 |

---

在 **方案 A（等深坑）/ 方案 B（分批入场）** 中推荐一条，**由出资人拍板**。

### 2.3 自测：先算预期，再跑代码核对

加仓金额公式：`加仓额 = min(单次上限, 货基余额 × 比例上限)`，且不超过货基余额本身。

| 场景 | 输入 | 预期 inspector 输出（先手算，再跑代码核对） |
|------|------|--------------------------------------------|
| 方案 A（等深坑） | PE分位 = 18%（<20%）+ 货基 ¥300 | 触发：可加仓 `min(¥500, 50%×300=¥150)=¥150`；提示"极度低估，考虑加仓 ¥150" |
| 方案 B（分批） | PE分位 = 28%（<30%）+ 货基 ¥300 | 触发：可加仓 `min(¥300, 30%×300=¥90)=¥90`；提示"低估区间，可额外加仓 ¥90" |
| 任意方案 | PE分位 = 32%（≥30% 且 <70%） | **应静默不推**（pe_normal，不触发加仓也不提醒） |

> 跑之前先自己算出预期，代码跑出来对不上就回头查公式。

## 三、Cron 巡检：改成每日轻量 + 无情况静默

### 3.1 查现状：现有 Cron 配置

运行 `cron list`（或本项目自动化对应的查看命令，见 3.3），确认现有 Cron 状态。

### 3.2 重新设计：每日巡检的触发条件

推翻月度巡检，改用**每日轻量巡检 + 有情况才推**。

> 阈值要和任务书对齐，别另立一套：浮亏 **15% = 预提醒**（离任务书 20% 哨点还差一截）、浮亏 **20% = 任务书正式哨点**；浮盈 **20% = 接近止盈预提醒**（任务书止盈线 25%~30%）、浮盈 **25% = 止盈触发**。"预提醒"和"正式线"职责不同，别把 15% 写成新哨点。
> 另外：`inspector.py` 里已有的 `_check_skip()`（别跳投检查）要一并接进每日 Cron——"连续想跳过定投"是任务书看重的纪律问题，不能丢掉。

触发推送的条件：

| 条件 | 动作 |
|------|------|
| 浮盈 ≥ 20%（接近止盈） | 推送：接近止盈线，注意观察 |
| 浮亏 ≥ 15% | 推送：浮亏预警，检查是否偏离纪律 |
| PE 分位 < 30% | 推送：低估区间，止盈资金可考虑额外加仓 |
| PE 分位 > 70% | 推送：估值偏高，留意止盈机会 |
| 距下次定投日 ≤ 2 天 | 推送：定投提醒（金额、手数） |
| 无以上情况 | Cron 静默，不打扰 |

### 3.3 落地：给 inspector.py 加 should_push + 配 Cron（给实现合同，不替你写）

你要落地的两件事，合同如下：

1. **"无情况静默"机制**：现在 `inspect_once()` 永远返回一个非空 `summary` 字符串，Cron 没法判断"该推还是该静默"。请给返回 dict 增加两个字段：
   - `should_push: bool` —— 上面 3.2 任一条件命中即为 `True`，全不命中为 `False`；
   - `push_reasons: list[str]` —— 命中了哪些条件，便于 Cron 决定推什么。
   Cron 包装层只在 `should_push == True` 时推送；否则静默。
2. **更新 pe_low 提示词**：按 §二 你选定的执行方式（方案 A / 方案 B），把第 124 行那句"可分批加回"换成对应文案（含金额上限，见 §二 表格）。

**Cron 用哪个？** 本项目自动化走 `skills/dca-tools`（Day7 已封装）或 `tools/scheduler.py`，不是系统 crontab。先 `cron list`（或对应 Skill 的查看命令）确认现状，再新增"每日 09:00 轻量巡检"；双周定投提醒保留不动。
